# 判断の材料を出す

念入りにするか、どの段階で何で裏付けるかを判断するのは PO。お金・時間・社会からの信頼など、何を軸に判断するかは場面ごとに PO が決めるので、軸を先に決めない。エージェントは判断せず、判断の材料だけを出す。

## 決まり

- 「大きい・小さい」「念入りにすべき」「この守り方で十分」といった評価を書かない
- 確かめた事実と推測を分けて書く（例:「テストで確かめた」「仕様を読んだ限り」「推測」）
- 当てはまらない材料は「なし」と書く。空欄にしない（見落としと区別するため）
- 材料ごとに、主張や機能が破れたときの具体的な筋書きから書く。一般論（「データが壊れると困る」）にしない

## 材料

破れる主張や機能ごとに、次を表にして示す。

| 材料 | 書くこと |
|---|---|
| 筋書き | 誤った状態がどこで生まれ、何を経て、誰にどう見えるか |
| 気づき方 | 誰が、いつ、何で気づくか。エラーになるか、黙って誤るか |
| 広がり | 巻き込まれる機能・主張・データ。後の操作に波及するか |
| 戻し方 | 戻せるか、どうやって、どれだけ手間か |
| 起きうる経路 | どの経路で起きうるか。今ある守り（証明・テスト・実行時の確認、変異テストの検出力） |
| 外へ出るか | 秘密情報・個人情報・他人のデータが、意図しない相手や場所に出る経路があるか |
| 止まるか | 資源を使い切る、応答しなくなる経路があるか |
| 守りを強めた代償 | 実行時の確認や証明を足したときの、性能・手間・使い勝手の変化 |

例（`add` が登録のイベントを書かずに成功する場合）:

| 材料 | 内容 |
|---|---|
| 筋書き | 次の `list` で未着手に見える。別のセッションが同じタスクを始める |
| 気づき方 | 黙って誤る。PO が履歴を見るまで気づかない（推測） |
| 広がり | `list`・`take`・履歴の表示。データに残り続ける |
| 戻し方 | イベントを手で足せば戻る。どのタスクが該当するかの洗い出しが要る |
| 起きうる経路 | 保存の層の誤り。今の守りはテストだけ |
| 外へ出るか | なし |
| 止まるか | なし |
| 守りを強めた代償 | コミット前の確認で、`add` ごとに 1 行を読む |

## PO の判断の残し方

PO が判断したら、台帳に残す。念入りにする機能は `formal = true` にし、判断の理由を機能の `rationale` に書く。裏付けの予定は主張の `evidence` に書く。理由は PO の言葉で書き、材料の表を写さない。
