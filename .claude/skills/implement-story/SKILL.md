# ストーリーの実装

人（PO）はソースコードを読まない。PO が要求を決め、判断する。エージェントは判断せず、判断の材料を出す。PO が関わるのは、① 要求の確定、② 仕様と台本のレビュー、③ 完了の判断の 3 か所だけ。

Issue の読み書きは `gh` で行う（リポジトリは `TadahiroYamamura/quenta`）。

「コミットする」と書いた時点で、`git-commit` スキルでコミットする。1 回で 1 つのコミットにまとめず、目的ごとに分ける。台帳（`spec/assurance.toml`）を変えるコミットには、Issue の番号（`#5` など）をメッセージに書く。

## 1. 要求を確かめる（PO の ①）

`CLAUDE.md` の「Git」に従い、ストーリーのブランチを切る。

`gh issue view <番号> --comments` で、最初の要求を読む。受け入れ条件は完璧でない前提で読む。正は台帳。

未決の点と、読んでいて分からなくなった点を、主張の案の形で PO に聞く（例:「タスクの ID は重ならない。でよいか。案 A / B」）。`CLAUDE.md` の「人への質問」に従い、1 回に 1 つずつ、選択肢と推奨を添える。

- PO の答えが、そのまま主張の了承になる。台帳に書く（新しい用語・機能も、了承を得てから足す）
- 主張の理由（業務上の根拠、法令や規定の出典）を一緒に聞き、`rationale` に書く。分からなければ空のままにする
- 主張を足す・変えるたびに、`spec-auditor` に、台帳のほかのすべての主張と矛盾しないかを点検させる。矛盾があれば、PO に示して決め直す
- 質疑の経過（何を聞き、どう答えたか）を、Issue にコメントで残す

質疑が終わったら、次を一度に示し、確認を得る。

- 足した・変えた主張の一覧。主張ごとに、どの段階で何で裏付けるかの案を 1 行で添える（`CLAUDE.md` の「保証の台帳と用語集」の手段から選ぶ）
- 念入りにする機能（`formal = true`）の案
- それぞれの判断の材料（`judgment-material` スキル）。念入りにするか、裏付けをどうするかを PO が判断するため。評価は書かない

PO の決定を台帳に書く（念入りにする機能は `formal = true` と `rationale`、裏付けの予定は `evidence`）。コミットする。

## 2. 仕様と台本を書く（PO の ②）

- 念入りにした機能の状態と操作を、Dafny で書いて証明する。関わる主張には `@assurance:claim`、型と操作には `@assurance:subject` の印を付ける。エラーは同値の補題で書く（`CLAUDE.md` の「エラーの扱い」）
- 操作の順番や同時実行が要るストーリー（複数のセッションの取り合い、セッションの途中の終了、時間の経過、「いつかは必ず〜になる」のような性質）では、Quint でも書いて検査する。#2 から使う
- 主張ごとに、E2E テストの台本を書く（`CLAUDE.md` の「E2E テストの台本」）。この時点では実装がないので、台本は失敗してよい
- 定義の決め方の一覧を作る。主張に書かれていないのに、仕様を書く中で自分で決めた定義（値の型、文字の範囲、状態の判定の書き方、境界の扱いなど）を挙げる。PO が問いを立てる手がかりにするため
- `spec-auditor` に、コメントと形式的な記述の食い違い、どの主張にも属さない定義がないかを点検させる。問題がなくなるまで、PO に示さない
- `spec-translator` に、念入りにした機能の仕様を自然言語に訳させる（逆翻訳）。台帳の主張は渡さない
- PO に、念入りにした機能の仕様、逆翻訳、主張の一覧（訳と見比べるため）、定義の決め方の一覧、E2E テストの台本、DB の構造の定義と移行（変えたなら）を示してレビューを受ける。`spec-auditor` の点検の結果や、それで直したことは示さない（PO が判断するのは、仕様と台本が要求どおりかだけのため）
- 指摘を受けたら、直す前に `CLAUDE.md` の「レビューの指摘の記録」に従って記録する。直したら、もう一度示す
- PO の了承を得るまで、次に進まない。了承を得たら、コミットする

## 3. 実装し、テストを書く

- 実装は普通の Go で書く。Dafny から生成したコードを本番のコードから使わない
- 実行時の確認を、台帳の予定どおりに入れる。確認を行う関数に `@assurance:check` の印を付ける
- テストを書く。`evidence` の印を付ける

| テスト | 対象と導き方 |
|---|---|
| モデルベーステスト・プロパティベーステスト | 念入りにした機能。`CLAUDE.md` の「モデルベーステストとプロパティベーステスト」に従う |
| E2E テスト | ② で書いた台本を通す。台本を変えたら、③ で変わった点を示す |
| 単体テスト | 判定や値の変換。列挙を `switch` で書き分けた箇所は、すべての値を回す |
| DB のインターフェースのテスト | SQLite への保存と読み出しで値が変わらないこと、同時の書き込み、移行 |
| CLI のインターフェースのテスト | 引数の解釈、JSON の出力の形、エラーコードと終了コード |
| 同時実行のテスト（Quint を書いたストーリー） | Quint で同時に起きうるとした操作を、複数の goroutine やプロセスから同時に呼び、`-race` を付けて実行する |

- 全部を `make check` で実行できるようにする（台帳の確かめ、証明・検査、テスト、変異テスト）。定型作業も `Makefile` に定義する。GitHub Actions で、Linux と macOS の実行環境の両方で `make check` を動かす
- 書き終えたら、目的ごとにコミットし、ストーリーのブランチをプッシュして、GitHub Actions の結果を確かめる

### 独立した点検を受ける
`test-auditor` に点検させる。渡すのは、Issue の番号。指摘があれば直し、もう一度点検させる。直すたびに、コミットする。

### 不具合を記録する
点検以降で見つかった不具合（点検の指摘のうち実装の誤りであるもの、PO が見つけたもの、使っていて見つかったもの）は、`report-bug` スキルで `bug` の Issue にする。自分で書いて自分で直したものは記録しなくてよい。直したら、コミットする。本文に `bug` の Issue の番号を書く。

### 構造を振り返る
作り終えた構造を点検する。人はコードを読まないので、構造の崩れに気づけるのはエージェントだけ。次の観点で見る。
- 同じ処理を何か所にも書いているか
- テストが書きにくかったか、テストの準備が長くなったか
- 次のストーリー（`story` の Issue）を入れるとき、どこをどう変える必要があるか。変える範囲が広いなら、先に構造を整える（下準備の）リファクタリングを提案する

苦しい点があれば、`CLAUDE.md` の「リファクタリング」に従って `refactor` の Issue にする。このストーリーの中では直さない。

## 4. 完了の判断を受ける（PO の ③）

`make story-evidence ISSUE=<番号>` の表を、Issue のコメントに貼る。欠けがあれば、示す前に埋める。そのうえで、PO に次を示す。ソースコードは示さない。

- `make story-evidence` の表（裏付けの予定と実際）。DB の制約は、PO が読むファイルの場所
- ② から変わった仕様・台本・DB の構造（あれば）
- 実行時の確認の検出力（変異テストで、確認が捕まえた変異の割合）
- 変異テストの除外の一覧で、このストーリーで足したもの
- 全部を実行した結果（手元と、GitHub Actions の Linux・macOS）
- このストーリーで記録した `bug` の Issue と、作った `refactor` の Issue の一覧（なければ「なし」と、点検した観点）
- PO が判断に迷いそうな点（あれば。判断の材料を添える）

指摘を受けたら、直す前に `CLAUDE.md` の「レビューの指摘の記録」に従って記録する。直したら、コミットする。

コミットは PO の承認を待たずに行ってよい。ストーリーのブランチ（`<Issue 番号>/...`）は、PO の指示なしにプッシュしてよい。`develop` へのプッシュ、PR の作成、`develop` へのマージは、PO の指示があったときだけ行う。
