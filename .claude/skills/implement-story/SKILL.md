# ストーリーの実装

人はソースコードを読まない。人がレビューするのは、仕様、受け入れ条件とテストの対応、テストの結果、Issue だけ。人に判断を求めるときは、この形で材料を出す。

Issue の読み書きは `gh` で行う（リポジトリは `TadahiroYamamura/quenta`）。

## 手順

「コミットする」と書いた時点で、`git-commit` スキルでコミットする。1 回で 1 つのコミットにまとめず、目的ごとに分ける（`git-commit` の手順 2）。

### 1. ストーリーを読む
`CLAUDE.md` の「Git」に従い、ストーリーのブランチを切る。

`gh issue view <番号> --comments` で、受け入れ条件、決まっていること、未決の点、範囲外のものを確かめる。既存の仕様（Dafny・Quint）や `CLAUDE.md` の「実装の制約」と食い違う点があれば、作業を始める前に人に聞く。

### 2. 未決の点を決める
未決の点と、読んでいて新たに分からなくなった点を、推測で埋めずに人に聞く。`CLAUDE.md` の「人への質問」に従い、1 回に 1 つずつ、選択肢と推奨を添えて聞く。決まったことは Issue にコメントで残す。ストーリーをまたいで効く決定は、振る舞いなら仕様に、実装の制約なら `CLAUDE.md` の「実装の制約」に書く。

`CLAUDE.md` を変えたら、コミットする。

### 3. 仕様を書く（人のレビュー 1 回目）
- 状態と操作を Dafny で書き、証明する
- 次のどれかに当てはまるストーリーでは、Quint でも書き、検査する。Dafny は 1 回の操作の前後の性質を証明するが、操作の順番や組み合わせで起きることは表しにくいため
  - 複数のセッションが同時に操作する（取り合い、同時の書き込み）
  - セッションが途中で終了する
  - 時間の経過に依存する（期限、古いものの掃除）
  - 「いつかは必ず〜になる」「行き止まりにならない」のような、操作の列についての性質がある
- Quint で書くときは、Dafny と同じ操作を同じ意味で書く。2 つの仕様の対応（Dafny のどの関数が Quint のどの action に当たるか）を表にする。食い違いは、手順 5 のモデルベーステストで見つける（実装は Dafny から生成するので、Quint の手順を実装で再生すれば、2 つの仕様のずれが表れる）
- Quint の検査は、不変条件（成り立つことを期待するもの）と、設計の穴を示す性質（反例が出ることを期待するもの）を分ける。反例が出たら、その手順を人に示す
- 受け入れ条件の各項目が、仕様のどこで表されているかの対応表を作る
- 人に、仕様のファイルと対応表を示してレビューを受ける。指摘を受けたら、直す前に `CLAUDE.md` の「レビューの指摘の記録」に従って記録する。直したら、もう一度示す
- 人の了承を得るまで、次に進まない
- 了承を得たら、コミットする

### 4. 仕様の外のコードを書く
Dafny から Go を生成し、SQLite、CLI、値の変換を Go で書く。生成したコードは手で直さない。

書き終えたら、コミットする（例: 依存の追加、`Makefile`、保存の層、CLI を、それぞれ別のコミットにする）。

### 5. テストを書く
| テスト | 導き方 |
|---|---|
| プロパティベースのテスト | Dafny の仕様の性質（不変条件、事後条件、補題）から導く。無作為な操作の列を実装に送り、毎回その性質が成り立つかを確かめる |
| モデルベーステスト（Quint を書いたストーリーだけ） | Quint のシミュレーションで操作の列を作り（`quint run --out-itf`）、その列を実装で再生して、各歩の結果と状態が仕様と一致するかを確かめる。手順のファイルを作り直すスクリプトも用意する。Quint の反例（設計の穴を示すもの）は、具体的な操作の列のテストにする |
| 同時実行のテスト（Quint を書いたストーリーだけ） | Quint で同時に起きうるとした操作を、実際に複数の goroutine やプロセスから同時に呼び、Quint の不変条件が成り立つかを確かめる。`-race` を付けて実行する |
| 単体テスト | 仕様の外のコード（値の変換など）の判定 |
| DB のインターフェースのテスト | SQLite への保存と読み出しで、値が変わらないこと。同時の書き込み |
| CLI のインターフェースのテスト | 引数の解釈、JSON の出力の形、エラーコードと終了コード |
| E2E テスト | ビルドした CLI を実際に呼び、受け入れ条件を 1 項目ずつ確かめる。テスト名に受け入れ条件の番号を入れる |

全部を `make check` で実行できるようにする（証明・検査を含む）。定型作業（Go の生成、ビルドなど）も `Makefile` に定義する。GitHub Actions で、Linux と macOS の実行環境の両方で `make check` を動かす。

書き終えたら、コミットし、ストーリーのブランチをプッシュして、GitHub Actions の結果を確かめる。

### 6. 独立した点検を受ける
`test-auditor` エージェントに点検させる。渡すのは、Issue の番号、仕様のファイル、テストのファイル。指摘があれば直し、もう一度点検させる。指摘を直すたびに、コミットする。

### 7. 不具合を記録する
手順 6 以降で見つかった不具合（点検の指摘のうち実装の誤りであるもの、人が見つけたもの、使っていて見つかったもの）は、`report-bug` スキルで `bug` の Issue にする。手順 3〜5 の途中で、自分で書いて自分で直したものは記録しなくてよい。

不具合を直したら、コミットする。本文に `bug` の Issue の番号を書く。

### 8. 構造を振り返る
作り終えた構造を点検する。人はコードを読まないので、構造の崩れに気づけるのはエージェントだけ。次の観点で見る。
- 仕様と仕様の外のコードの対応が込み入ってきたか（値の変換が増えた、仕様にない分岐が仕様の外に増えた）
- 同じ処理を何か所にも書いているか
- テストが書きにくかったか、テストの準備が長くなったか
- 次のストーリー（`story` の Issue）を入れるとき、どこをどう変える必要があるか。変える範囲が広いなら、先に構造を整える（下準備の）リファクタリングを提案する

苦しい点があれば、`CLAUDE.md` の「リファクタリング」に従って `refactor` の Issue にする。このストーリーの中では直さない。

### 9. 人に示す（人のレビュー 2 回目）
次を示す。ソースコードは示さない。
- 仕様（手順 3 から変わった点）
- 受け入れ条件と E2E テストの対応表
- 仕様の性質とテストの対応表（Dafny の性質とプロパティベースのテスト、Quint の性質とモデルベーステスト・同時実行のテスト）
- Quint の反例（あれば。操作の列として）
- 全部を実行した結果（手元と、GitHub Actions の Linux・macOS）
- このストーリーで記録した `bug` の Issue の一覧
- 手順 8 で作った `refactor` の Issue の一覧（なければ「なし」と、点検した観点）
- 人が判断に迷いそうな点（あれば）

指摘を受けたら、直す前に `CLAUDE.md` の「レビューの指摘の記録」に従って記録する。直したら、コミットする。

コミットは人の承認を待たずに行ってよい。ストーリーのブランチ（`<Issue 番号>/...`）は、人の指示なしにプッシュしてよい（GitHub Actions の結果を確かめるため）。`develop` へのプッシュ、PR の作成、`develop` へのマージは、人の指示があったときだけ行う。
