# 保証の強さを決める

性質が破れたときに何が起きるかで、その性質に必要な守り方の強さが決まる。故障モード影響解析（FMEA）で、影響の大きさと検出しやすさから対策の強さを決める考え方を借りている。

## 手順

性質（`spec/guarantees.toml` の行）ごとに、次の順で決める。

1. 4 つの軸の段階を決める（下の「影響の軸」）。機能への影響は、`primary-functions.md` の一覧で、その性質が主要な機能と副次的な機能のどれに関わるかを見て決める。一覧にない機能に関わるなら、決めずに人に聞く
2. 軸ごとに、下の「必要な守り方」の表で要求（①〜⑤）を引き、最も強いもの（番号の小さいもの）を、その行に必要な守り方とする
3. 必要な守り方を満たす守るもの（証明、DB の制約、実行時の確認、テスト、人のレビュー）を選ぶ。満たせないなら、人に判断を仰ぐ
4. `spec/guarantees.toml` の行に、`harm`・`data`・`function`・`detectable` と、選んだ守るものを書く。軸の段階は、エージェントが案を付け、仕様のレビューで人が確かめる

## 影響の軸

| 軸 | 段階（軽い → 重い） | `spec/guarantees.toml` の項目 |
|---|---|---|
| 人やお金への影響 | なし → 損害 | `harm` |
| データへの影響 | なし → 不整合 → 喪失 | `data` |
| 機能への影響 | なし → 細部 → 副次 → 主要 | `function` |
| 気づけるか | 気づける → 気づけない | `detectable` |

| 段階 | 内容 | 例 |
|---|---|---|
| 人やお金の損害 | 人の安全や、お金に損害が出る | （quenta にはない。給与やシフト、在庫など、ほかのプロダクトで起きうる） |
| データの喪失 | データや経緯が失われる。または、残っている情報から正しい状態を特定できなくなる（DB を直接編集できても、何に直せばよいか分からない） | イベントが消える、ID が重なって 2 つのタスクの中身が混ざる |
| データの不整合 | データが矛盾しているが、残っている情報から正しい状態を特定でき、直せる | タスクの状態と、最後のイベントが食い違う（イベントの列から正しい状態が分かる） |
| 主要な機能を失う | `primary-functions.md` の主要な機能を果たせない、または誤った結果を返す | 一覧から終わっていないタスクが漏れる |
| 副次的な機能を失う | `primary-functions.md` の副次的な機能を果たせない、または誤った結果を返す | 古い終わったタスクを掃除できない |
| 細部 | 見た目・順番・出力の細部が違う | 一覧の並び順、エラーの説明文 |
| 気づける | 守るものがすべて外れたときに、エラーになる、または終了コードで失敗が分かる | 理由なしで完了しようとして、エラーが返る |
| 気づけない | 守るものがすべて外れたときに、正常に終わる。結果を見ても、誤りだと分からない | 終わったタスクが、何も言われずに `todo` に戻る |

- データと機能は別の軸として評価する。1 つの性質が、両方に響くことも、片方だけに響くこともある（例: 一覧からタスクが漏れるのは、データへの影響はなく、主要な機能を失う）
- データの不整合で気づけないものは、軽く扱わない。DB は直せても、気づかないうちに AI がその誤った状態をもとに進めた作業は、元に戻らないため
- 「気づけるか」は、守るものがすべて外れたときで評価する。実行時の確認を足すと「気づけない」が「気づける」に変わるが、実行時の確認は守るものの 1 つとして書き、「気づけるか」の評価は変えない（実行時の確認を足しただけで、ほかの守りが要らなくなるのを防ぐため）
- 気づけないものを重く見るのは、使う側の AI が成功したと信じて次の作業に進み、誤りの上に作業が積み重なるため

## 必要な守り方

| 影響 | 気づける | 気づけない |
|---|---|---|
| 人やお金の損害 | ① | ① |
| データの喪失 | ① | ① |
| データの不整合 | ③ | ②（加えて、不整合を検査できる仕組みで「気づける」に変えられること） |
| 主要な機能を失う | ③ | ② |
| 副次的な機能を失う | ⑤ | ④ |
| 細部 | ⑤ | ⑤ |
| なし（その軸に影響がない） | 要求なし | 要求なし |

| 強さ | 必要な守り方 |
|---|---|
| ① | 証明か DB の制約。テストだけで守ることは認めない |
| ② | 証明か DB の制約。テストだけで守るなら、人の了承（`approved`）を得て、その経路をわざと起こすテストと、変異テストでその判定を壊すと落ちることの確認を必須にする |
| ③ | 証明、DB の制約、またはテスト（変異テストでその判定を壊すと落ちることを確かめる） |
| ④ | テスト（変異テストでその判定を壊すと落ちることを確かめる）、または実行時の確認（確認がはたらくことをテストする） |
| ⑤ | テスト、または人のレビュー |

- 「証明」と書けるのは、実装がその Dafny の関数を実際に呼ぶときだけ。手本として書いた関数（実装は同じことを Go や SQL で行う）で証明した性質は、ほかの守り方で守る
- 守るもの「なし」は、①〜④では認めない。⑤でも、人の了承（`approved`）が要る
- 前提の行は、それを前提にする行と同じか、より強い守り方を要する（番号が同じか小さい）。強い守りを要する性質の前提が、弱い守り方で済まされないため
