# コミット

コミットは、人の承認を待たずに行ってよい。ストーリーのブランチ（`<Issue 番号>/...`）は、人の指示なしにプッシュしてよい（GitHub Actions の結果を確かめるため）。`develop` へのプッシュ、PR の作成、`develop` へのマージは、人の指示があったときだけ行う。

## 手順

### 1. 変更を把握する
`git status`・`git diff`・`git diff --cached` で変更の全体を把握する。コミットするものがなければ終える。

### 2. コミットの単位を決める
- 目的が異なる変更は分ける（バグの修正とリファクタリングを混ぜない、など）
- 変更が 1 つのファイルだけでも、目的が異なれば分ける
- Dafny から生成した Go はコミットしない（`.gitignore` に入っているはず。入っていなければ足す）

### 3. コミットする
コミットごとに、対象のファイルだけをステージしてコミットする。`git add -A` や `git add .` は使わない。

```bash
git add <files>
git commit -m "$(cat <<'EOF'
(type) subject

body
EOF
)"
```

コミットしたら、`git log` で内容を確かめる。

## コミットメッセージの規約

### 形式

```
(type) subject

body
```

- `(type)` は小文字。複合する場合は `(chore|docs)` のようにパイプで結ぶ
- type と subject の間に、スコープやコロンは入れない

### type

| type | 用途 |
|---|---|
| `feat` | 新機能の追加 |
| `fix` | バグの修正 |
| `docs` | ドキュメントだけの変更 |
| `refactor` | 動作を変えないコードの整理 |
| `test` | テストの追加・修正 |
| `chore` | ビルド・設定・依存関係などの雑務 |

### subject

日本語で、動詞で終える（例: `〜を追加する`、`〜を修正する`、`〜に変更する`）。

### body

- 平文の日本語の散文で書く。`## 意図` のような見出しは使わない
- 「なぜこの変更をしたか」を中心に書く。何を変えたかは差分で分かるので書かない
- 関係する Issue の番号を書く（例: `#1`）
- subject だけで意図が自明な場合は省略してよい（Issue の番号だけは書く）

| 書く | 書かない |
|---|---|
| 変更の意図・きっかけ | 何を変えたか（差分を見れば分かる） |
| 差分から読み取れない、その時点の事情（暫定の対応、移行の途中など） | コードが存在する限り正しい理由（コメントに書く） |
| 検討の経緯（なぜ別の案にしなかったか） | 既知の懸念・今後の課題（Issue に書く） |
| 削除・置き換えの理由 | |
