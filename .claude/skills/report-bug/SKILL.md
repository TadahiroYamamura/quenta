# 不具合の記録

このリポジトリは、人がソースコードを読まない開発で何が起きるかを観察している。不具合の記録は、その観察の材料になる。直すことと同じくらい、どこで見つかり、どの層で起き、コードを読まずに直せたかを残すことが大事。

## 記録する場面

- テストの監査（`test-plan-auditor`・`test-detection-auditor`・`test-quality-auditor`）の点検で見つかった、実装やテストの誤り
- 人のレビューで見つかったもの
- 実際に使っていて見つかったもの
- 人が「コードを読まないと分からない」と感じた場面（不具合でなくても記録する）

ストーリーの実装中に、自分で書いて自分ですぐ直したものは記録しない。

## Issue の書き方

`gh issue create -R TadahiroYamamura/quenta --label bug` で作る。タイトルは現象を 1 文で書く。本文は次の節を持つ。

```
## 現象
何が起きたか。期待した振る舞いとの違い。

## 再現手順
CLI のコマンドの列、またはテストの名前。

## 関係するストーリー
#<番号>

## 観察
| 項目 | 内容 |
|---|---|
| どこで見つかったか | 証明 / Quint の検査 / プロパティベースのテスト / モデルベーステスト / 同時実行のテスト / 単体テスト / DB のテスト / CLI のテスト / E2E テスト / テストの監査の点検 / 人のレビュー / 実際の利用 |
| どの層か | 仕様の誤り / 仕様の書き漏れ / 仕様の外の Go / 生成したコード / 道具（Dafny・Quint・Go） / SQLite / テストの誤り / 不明 |
| コードを読まずに直せたか | 直せた / 人がコードを読まないと判断できなかった（何を読みたくなったか） |
| 人の手間 | 人が判断した回数、やりとりの回数 |

## 原因
分かっていれば書く。分からなければ「調査中」。

## 対応
どう直したか。直したコミットや PR を書く。
```

直したら、「対応」を書き足してから Issue を閉じる。
